Do not read those numbers off this table next time. They are a claim with a date on it:

```sh
./gradlew test staleComments --rerun-tasks --no-build-cache
```

`--rerun` alone is a trap: it forces only the *requested* task, so every per-module `test` stays
`UP-TO-DATE` and the suite reports a green that is hours old. Check the result XMLs' modification
times, not the `BUILD SUCCESSFUL` line.

## What this session did

The cohesion ledger (`docs/plans/cohesion-ledger.md`), start to finish. **Every numbered item
1–16 is resolved.** Five of them turned out not to be defects and say so with the evidence, which
matters more than the ten that were: they will otherwise be re-found and re-"fixed".

Four live bugs came out of the sweep rather than out of the list:

1. **The app picker's third row was clipped by 18dp** on the Konker (338dp of panel, 356dp of
   grid). Only on the smaller handheld, which is why it survived.
2. **F1 was bound to nothing** while four sheets printed "F1 Apply" in their footer.
3. **The charging shimmer redrew behind every full-screen page** — 723 frames over 12 seconds on
   the app drawer, for an icon that was not on screen. **Measured**, before and after.
4. **The music browser's search box reset the caret** on every keystroke.

And two tests that could not fail were replaced by tests that can. Both are worth knowing about
because the trap is reusable:

- `boundsInRoot` **is clipped to the viewport**, so a Compose row pushed off the bottom of the
  screen reports a tidy in-bounds rectangle and every "does it fit" assertion passes. Assert the
  *sum* of the row heights instead — `XmbLetterRailFitTest` is the pattern.
- An assertion of the form `occurrences <= 1` passes at zero. The hint-bar test asserted that at
  most one prompt named the sort knob, and went on passing after the prompt was deleted.

## Open, in the order I would take them

### 1. N2 — the tablet's dead space (`docs/plans/performance-and-responsive-plan.md`)

**Verified by measurement** on the real NP05J (1067×668dp landscape) on 2026-09-25: Settings' root
leaves ~204dp below the last row and ~545dp to the right of the list column; the XMB home draws 4
categories on a panel that would hold many more.

The App Drawer is **not** on that list and the measurement says why: its APPS tab looked empty
because that tab's "rest" list is five items. On the GAMES tab, with 66 apps, the grid fills the
panel. Measure a long list before changing anything there.

**The constraint that is the actual work:** `GridCells.Adaptive` breaks D-pad navigation on every
device unless the measured column count is fed back into `moveSearch` / `gridMove`. The grid
change is the easy half. `StudioGridCapacity` is the pattern — it sizes by measurement and its
rule is "a larger screen gets more columns and rows, never bigger tiles".

### 2. N3 — the wave while another app is foreground

Owner's framing: *"the wave stops when another app is up."* The shimmer half of this is done and
measured. The animated background itself is **unmeasured** — nothing here is verified. Start by
measuring, not by editing: `rememberInfiniteTransition` costs a frame per vsync only when its
value is read in a draw scope, which is what made the shimmer fix a one-line guard.

### 3. N4 — the Titan's keyboard as a swipe surface

The Titan Elite's capacitive keyboard reports `KEYBOARD | TOUCH | TOUCH_MT` on `sub_touch`. Owner
wants swipe gestures off it. **Unscoped, and it needs the device** — the emulator cannot produce a
second touch device.

### 4. Item 13 — named type sizes. **Do not do this as written.**

The ledger's entry explains it at length. Short version: collapsing the sizes would merge two that
look like drift and are not. The detail panel's 8sp and the Studio's 10.5sp sit in two different
scaling contexts — one inside the XMB canvas, which carries the cross's auto-fit *on top of* the
user's scale, and one on a chrome screen that takes neither. A size chosen against the reference
at 1× already came out a third too big once.

Owner said "yes collapse" before that was known. It is worth re-asking.

## Known bad, accepted

`DisplaySettingsViewModel*Test` flakes under full-suite load and **moves between classes** — it
has timed out in `FontColorTest` and in `GameBootTest`, both at the 60s wall clock. Owner's call
on 2026-09-25: **ignore it.**

`AudioSettingsViewModelTest` failed four cases in an interrupted background run on 2026-09-26 and
passed in the full gate the same day. **I did not inspect why it failed**, so whether that is the
same DataStore race or something else is a lead, not a finding.

**The rollback nearly took the mitigation out with it, and this is the useful part.** Three of the
four classes had gained `io = dispatcher` inside `0143e141` — a commit that is otherwise about
button labels and empty states. Reverting the range stripped it, and the very next full sweep went
red in `GameBootTest`. Those 15 test-only lines were restored by hand and are the only thing in the
tree that differs from `5f3f4eaa`:

```sh
git diff v1.13.0 5f3f4eaa --stat     # expect: 3 test files, 15 lines
```

The lesson is not about this flake. **A revert by commit range moves whatever else rode in those
commits**, and a mitigation for an accepted flake is exactly the kind of passenger nobody thinks to
look for — the suite going red is the only thing that tells you.

Recorded so nobody re-diagnoses it from scratch: **the race is DataStore's, not the ViewModel's.**
All four classes now inject the ViewModel's dispatcher, which removes half of it; `pfpDataStore`
keeps its own scope and threads, which is the half that still bites. Raising the budget is not a
fix — it went 10s → 60s once already and still times out.

**It is a flake, not a red test. One green sweep says nothing about it in either direction.** I
claimed it fixed on a single green run in this session and it failed again two commits later.

## Things you will want and would otherwise hunt for

**Emulators that match the hardware.** `tools/emu/README.md`. Three AVDs whose app-visible config
matches the three real devices; the script prints WindowManager's configuration after boot and
that line is the check. If it does not match the `expected` line, nothing measured on that AVD is
worth anything.

**Dummy content.** `tools/emu/make-content.py` and `CONTENT.md` — one game, video, image, book and
song, generated and verified to scan.

**The stale-comment check.** `./gradlew staleComments`, baselined at `tools/stale-comments/baseline.txt`
by `file::symbol` so code moving inside a file does not invalidate an entry. It fails on a *new*
comment naming something the same change deleted, which is the mistake this codebase repeats. It
caught one of mine the same hour it was wired.

**The signing key is on this machine only** and is gitignored. Lose it and no build can ever
upgrade an installed copy.

**`local.properties` holds ScreenScraper credentials** and is gitignored. That account allows
`maxthreads = 1`, so the concurrency work in the scraper is correct and cannot be exercised.
