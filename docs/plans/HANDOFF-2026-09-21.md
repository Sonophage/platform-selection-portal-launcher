## Next, in the order I would do it

### 1. Wire the Steam provider into a scrape run *(half-finished, highest value)*

`SteamStoreApi` exists, is tested, and **nothing calls it**. The commit says so. It needs a caller
in the scrape path for Windows games.

Why it is worth doing first: all 8 Windows games already carry a Steam app id in
`games.storefront_game_id`, so there is no matching step — and Steam publishes a hero, box art and
a **transparent logo** at URLs derived from the id, which is exactly the three assets the drill
flyout composes and exactly what those games lack. No API key.

Where to hook it: `ArtworkRepository`'s scrape modes, alongside the four existing providers.
`ProviderCapabilities[MatchProvider.STEAM_STORE]` already says it supplies both metadata and
artwork and cannot be title-searched.

### 2. The title↔logo collision in the drill flyout *(a legibility bug, cheap)*

In `drill-01`-style views the row title is drawn **over** the PIC0 logo's own letterforms. Reported,
and visible in the sweep captures. Cause as reported: `XmbDrillFlyout` never receives
`focusedLogoVisible`, so `XMBItemList.kt:641` keeps the title up while `XMBShell.kt:650` draws the
logo. Related and in the same area: `XMBShell.kt:871` passes `focusedLogoVisible = pic0Alpha > 0f`,
so the title disappears on the *second frame* of a 500 ms fade — roughly 650–1150 ms where the
focused game has no legible name. Crossfading the two instead of cutting fixes both.

**Verify before acting.** I confirmed the `pic0Alpha > 0f` line in source but never watched the
collision happen on the device.

### 3. Category verbs into a submenu *(the one item from the owner's six I did not finish)*

He chose this (option 4b): collapse *Move to / Add to / Remove from / Pin to Category* into one
`Category ▸` submenu, and leave the rest of the menu alone. The app already has the submenu idiom —
it shipped in 1.4 for the Add rows. Menu is built in `XMBViewModel.openGameContextMenuCore`; the
four verbs are around `:5691`.

Context: a review counted 9 rows fitting on screen and up to 16 buildable for a multi-disc Windows
game in a collection in a custom category.

### 4. Finish `Modifier.menuCursor()` adoption

Five hand-rolled focus borders remain, at different radii and widths (1dp/7dp, 1dp/8dp, 1.5dp/8dp,
2dp/CircleShape). `SearchScreen` was converted this session; `MusicTrackPicker`,
`MusicBrowserScreen`, `CollectionPickerPanel`, `GameDetailScreen` and `WizardRows` were not.
Mechanical.

### 5. Scraper region and language preference

The one genuine capability gap found against NeoStation. `SsMediaSelection.kt:42` hardcodes
`us → wor → null → other`, and `ScreenScraperApi` hardcodes `us`/`wor` for title and date and `en`
for synopsis. **Verified absent**: zero hits for `regionPriority|preferredRegion|scrapeRegion|
scrapeLanguage`. A PAL- or JP-preferring library cannot be expressed. One preference plus a
comparator.

### 6. The paged game-detail card *(the NeoStation layout idea, needs judgement)*

Their detail screen is a `Stack`: fixed tab strip pinned top, **fixed-height** footer bottom, and
one horizontally-sliding strip of panels walked with the shoulder buttons. Their design size is
640×480, near-identical to our 462dp, so the proportions transfer: 46 header + 96 footer + 338
content.

Ours is one vertical scroll column, so the media strip and info band sit below the fold. The two
details worth more than the shape: the footer height is constant *on purpose* so nothing reflows as
the cursor moves, and tabs a game cannot fill are **absent, not disabled**, so the cursor index
resolves against what is visible.

## Do not re-litigate these

Each was checked and settled this session:

- **The settings rail is not broken.** It centres on the cursor *or* the open screen, every pane
  scrolls with keep-in-view, and there **is** a bottom fade (16dp, `DstIn`, sharing its constant
  with keep-in-view). A review claimed "no fade anywhere in 26 shots" — wrong about the code. A
  second claim that "11 of 26 panes are cut off" was a count off screenshots taken *before* the rail
  and row-height fixes; the comment at `SettingsScaffold.kt:1616` now says which half was measured.
- **The app drawer keeping publisher icon tiles is defensible.** A grid of apps may look like an app
  grid; a crossbar row beside monochrome glyphs may not.
- **`getMonochrome()` is the wrong icon fix.** It is API 33, and it returns null for the legacy
  icons that are the actual problem. The foreground-layer strip plus one shared container shape is
  what shipped, and the container is what carries it — the Play Store is adaptive and *still*
  renders a white tile, because its foreground contains one.
- **`StorefrontAppDrawer.kt` is intentionally dead code**, preserved for a future RSS feature. Its
  file header says so. Do not treat anything in it as a live bug.
- **The settings help band is deliberate** and so is the reserved footer height; only the divider
  drawing at full strength under a faded hint was wrong, and that is fixed.

## Gotchas

- **Never press A on a game.** From the game detail page, A is Play — it launched GameNative
  mid-screenshot-run and nine captures went into another app's UI before I noticed. Use Y for
  Options. There is a focus-guarded capture helper pattern worth rebuilding: send keys, read
  `dumpsys window | grep mCurrentFocus`, and abort unless it matches `psplauncher`.
- **Two assertion libraries.** `org.junit.Assert.assertEquals(message, expected, actual)` puts the
  message **first**; `kotlin.test` puts it **last**. Files mix them and `kotlin.test.Test` tells you
  nothing. Prefer the 2-arg form; grep the file's imports before writing a 3-arg one.
- **`Uri.parse` returns null in plain JVM tests.** A "pure" helper that uses it is not pure and will
  answer null for everything under test. `musicArtStillOnDisk` does its own string handling for
  exactly this reason.
- **A nullable return can make a test decorative.** `assertNull(helper(...))` passed under the broken
  version too, because "found nothing" and "nobody asked" were the same value. `ThumbAction` and
  `AppIconArt`-style sealed results exist to stop that; prefer them where the two outcomes differ.
- **Falsify in the same sitting.** Break the production code, confirm the *named* assertion goes red
  and its siblings stay green. One test this session re-implemented its own policy locally and
  stayed green when the real code broke.
- **The device PIN** is used only in an `adb shell input text` unlock and must never be written to a
  file, commit or log.
- **`keystore.properties` and `local.properties` are gitignored and hold credentials.** Do not
  create the signing key; that identity stays the owner's.
